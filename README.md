# itg-rag

Учебный RAG mini-product: локальные документы → чанки → embeddings → Weaviate → поиск → ответ с проверяемыми источниками.

CLI работает с реальным Weaviate и OpenAI-совместимыми API для генерации и embeddings. В репозитории есть 8 документов вымышленного магазина «Полка» и 12 проверочных вопросов: 8 с ответами и 4 без ответа в базе. Все контакты, адреса и правила магазина учебные.

## Быстрый запуск

Нужны `uv`, Python 3.13 (uv может установить его автоматически), Docker Desktop с запущенным сервером и ключ API. Выполняйте команды из корня репозитория.

```sh
uv sync --locked
cp .env.example .env
```

Заполните `.env`:

```dotenv
OPENAI_API_KEY=your-key
OPENAI_BASE_URL=
OPENAI_MODEL=gpt-4.1-mini
EMBEDDING_MODEL=text-embedding-3-small
```

Пустой `OPENAI_BASE_URL` использует стандартный адрес OpenAI. Для совместимого провайдера укажите его URL и точные имена доступных моделей. Если chat и embeddings работают у разных провайдеров, заполните `EMBEDDING_API_KEY` и `EMBEDDING_BASE_URL`; иначе они наследуются от `OPENAI_*`. Embedding-модель должна поддерживаться именно endpoint `/embeddings`.

```sh
make up
make load
make chunks
make ingest
make stats
make ask QUESTION="В какой срок можно вернуть исправный товар в Полку?"
```

`make up` ждёт готовности Weaviate. HTTP доступен на `127.0.0.1:8080`, gRPC на `127.0.0.1:50051`. Данные сохраняются в Docker volume `weaviate_data`. Локальная конфигурация использует анонимный доступ и открывает порты только на loopback.

```sh
make down
```

Эта команда останавливает сервис с сохранением данных. Следующий `make up` использует тот же индекс.

## Своя база знаний

Положите UTF-8 файлы `.txt` или `.md` в `knowledge_base/`, включая вложенные папки, и выполните `make ingest`. Другой каталог задаётся через `KNOWLEDGE_DIR`. Имя источника — путь относительно каталога базы.

Загрузчик нормализует Unicode и пробелы, убирает пустые строки и пропускает пустые документы. Отсутствующий каталог, полностью пустая база и файл с некорректной кодировкой приводят к понятной ошибке. Символические ссылки не загружаются.

Chunking по умолчанию: до **900 символов**, overlap **150 символов**. По возможности граница проходит по пробелу или переводу строки. Это символы, а не токены. У чанка есть `document_id`, `source_name`, `chunk_id`, `text`, `start`, `end`; offsets относятся к очищенному тексту.

`document_id` определяется относительным путём файла, `chunk_id` — документом и порядковым номером чанка. Повторная индексация обновляет объекты по стабильным UUID без дублей. Устаревшие чанки, в том числе из удалённых файлов, удаляются только после успешной записи текущих чанков. Команда синхронизирует **весь каталог** с выбранной collection; не используйте одну collection для независимых баз.

При изменении embedding-модели, endpoint или параметров chunking задайте **новое** `WEAVIATE_COLLECTION` и снова выполните `ingest`. Проверка fingerprint защищает от поиска в несовместимом индексе. API-ключ в fingerprint не входит. Переключение одной модели на другой backend под тем же именем требует новой collection вручную.

## Поиск и ответы

```sh
uv run itg-rag search "Сколько действует ссылка восстановления пароля?" --top-k 4
uv run itg-rag ask "Какую часть заказа можно оплатить бонусами Полки?"
uv run itg-rag ask "Сколько стоит доставка Полки в Берлин?" --output results/unknown.json
uv run itg-rag --verbose ask "Какая гарантия на настольные игры в Полке?"
```

Все результаты — JSON. `--output` сохраняет результат в файл; без него JSON выводится в stdout. Диагностика идёт в stderr. `load` показывает имена и длины документов; `chunks` — полный текст и метаданные чанков.

В `search` возвращаются top-k результатов semantic `near_vector` из Weaviate с cosine `distance`: меньшее значение означает большую близость. Это не вероятность правильности. `search` показывает все top-k, в том числе слабые результаты, чтобы можно было оценить шум.

В `ask` только результаты с `distance <= MAX_DISTANCE` передаются LLM. По умолчанию `TOP_K=4`, `MAX_DISTANCE=0.65`. Если подходящих результатов нет, LLM не вызывается. Затем отдельный вызов LLM проверяет, покрывает ли контекст все части вопроса о нужном предмете: правило для одной категории товара нельзя переносить на другую. При отрицательном решении генерация пропускается. Близость тем не гарантирует наличие ответа.

Ответ содержит:

- `status`: `answered` или `insufficient_context`;
- `answer`: ответ с отметками `[S1]`, `[S2]`;
- `sources`: выбранные цитаты, файл, ID документа и чанка, distance;
- `retrieved`: весь top-k для анализа поиска;
- `reason`: причина отказа — `weak_retrieval` или `context_cannot_answer`.

Источники ответа — `sources`, а не все элементы `retrieved`. Метка `[S1]` ссылается на `sources` с `label="S1"`. Файл находится в каталоге базы по `source_name`; точный использованный текст сохранён в `quote`.

### Как ограничены галлюцинации

В этом mini-product используется **экстрактивная генерация**: LLM получает вопрос и найденные чанки, выбирает дословные фрагменты, отвечающие на вопрос, и возвращает JSON по схеме Pydantic. Программа проверяет ID чанка и находит каждую цитату в его тексте, затем собирает ответ с источниками. Различия только в пробелах и переводах строк выравниваются к оригиналу; опубликованная цитата всегда является точной подстрокой источника. Изменения слов, чисел и пунктуации не принимаются. Непроверенный свободный пересказ модели в ответ не попадает.

Проверка достаточности контекста и генерация валидируются отдельно. После невалидного JSON, выдуманного источника или изменённой цитаты допускается одна повторная попытка соответствующего этапа. После второй ошибки команда завершается с ошибкой без публикации ответа. Отрицательная проверка достаточности или ответ модели с `sufficient_context=false` даёт честный отказ. После выбора цитат отдельная проверка подтверждает, что они покрывают все части вопроса. Неполная подборка получает одну повторную попытку. Успешный ответ обычно требует трёх chat-вызовов: проверка контекста, выбор цитат и проверка выбранного ответа.

Это гарантирует происхождение опубликованных цитат, но не доказывает их полноту, истинность или смысловую релевантность вопросу. За отбор по смыслу отвечает LLM. Инструкции из документов явно объявлены недоверенными данными в system prompt; полной защиты от prompt injection это не даёт. Не загружайте недоверенную базу как авторитетный источник.

## Демо и оценка качества

```sh
make demo
make evaluate
make compare
```

- `demo` запускает реальный RAG на `demo/questions.json` и сохраняет `results/demo.json`.
- `evaluate` проверяет только retrieval и сохраняет `results/retrieval.json`.
- `compare` дополнительно задаёт те же вопросы модели без контекста и сохраняет `results/comparison.json`.

Эти команды требуют работающий Weaviate и вызывают платный API. Демонстрация не подменяется записанными ответами. Для просмотра уже выполненной проверки без API откройте [demo/README.md](demo/README.md) и сохранённые JSON в `demo/`.

`expected_source_recall` — доля положительных вопросов, для которых ожидаемый файл попал в контекст после фильтра distance. `correct_behavior_count` проверяет ответ/отказ, `expected_terms_found` — наличие контрольных строк в ответе. Эти метрики не являются полной оценкой groundedness или semantic correctness. Полный текст выдачи сохранён для ручного анализа шума и цитат.

```sh
make verify-live
```

Полная live-проверка повторно индексирует текущую базу, проверяет отсутствие дублей, запускает 12 вопросов с RAG и без него, сравнивает три настройки chunking, выполняет интеграционный тест и обновляет артефакты в `demo/`. Экспериментальные collection создаются с уникальными именами и удаляются после проверки. Используйте эту команду с учебной базой из репозитория: набор ожидаемых источников привязан к ней.

## Проверки разработки

```sh
make check
make integration
uv build
```

`make check` работает без API и Docker: Ruff, проверка формата, ty, unit-тесты. Интеграционный тест по умолчанию пропускается; `make integration` запускает его на реальном локальном Weaviate, создавая и удаляя отдельную тестовую collection. Ключ API ему не нужен.

Тесты проверяют очистку, chunking без потери текста, offsets, стабильные ID, валидацию embeddings, ошибки API, ограниченные retries, цитаты и источники, слабый контекст, fallback, обработку ошибки одного вопроса в batch и CLI. Интеграционный тест проверяет запись, поиск, обновление без дублей, удаление устаревших объектов и несовместимость индексов.

## Структура

```text
src/itg_rag/
  config.py           настройки .env и fingerprint индекса
  loader.py           чтение и очистка UTF-8 документов
  chunking.py         разбиение с overlap и метаданными
  api.py              настройка SDK и безопасные ошибки
  embedder.py         batch embeddings и проверка векторов
  weaviate_store.py   schema, синхронизация, near_vector
  retriever.py        query → embedding → top-k
  prompts.py          инструкции и контекст
  llm_client.py       chat completions
  schemas.py          Pydantic-схемы
  rag_pipeline.py     distance gate, выбор и проверка цитат
  evaluation.py       вопросы, метрики и сравнение
  main.py             CLI

demo/                 вопросы и результаты live-проверки
scripts/              локальные и live-проверки
tests/                unit и integration
```

## Настройки и ограничения

Полный список переменных — в [.env.example](.env.example). Переменные окружения имеют приоритет над `.env`. Как и в `itg-llm`, используются `OPENAI_API_KEY`, `OPENAI_BASE_URL` и `OPENAI_MODEL`; SDK настроен на timeout 30 секунд и максимум 2 повтора временных ошибок. Постоянные HTTP 400/401/403/404/422 не повторяются. Тела API-ошибок и ключи не печатаются.

Поддерживаются только текст и Markdown в UTF-8; PDF, OCR, UI, FastAPI, hybrid retrieval и reranking не входят в scope. Индексация рассчитана на небольшую базу, выполняется одним процессом и не является транзакционной: при сбое во время записи возможна частично обновлённая collection; повторите `ingest` до следующего использования. Embeddings получаются заново при каждом ingest; локального кэша векторов нет.

Порог distance требует настройки под свою модель и корпус. Настройки по умолчанию проверены на учебной базе, а не на произвольных документах. Полные сведения о проверках и выполнении семи этапов — в [docs/development-report.md](docs/development-report.md).

## Если что-то не работает

- `Weaviate operation failed`: проверьте `docker compose ps`, готовность контейнера, HTTP и gRPC порты; логи — `docker compose logs --tail=100 weaviate`.
- Занят порт: поменяйте `WEAVIATE_HTTP_PORT`/`WEAVIATE_GRPC_PORT` в `.env`, пересоздайте сервис через `make up`.
- `Index does not exist`: выполните `make ingest` с текущими настройками.
- `Index configuration differs`: задайте новое `WEAVIATE_COLLECTION` и выполните `ingest`.
- HTTP 401/403: проверьте ключ и права; HTTP 400/404: endpoint и имя модели. Chat-модель и embedding-модель — разные настройки.
- `insufficient_context`: посмотрите `search`, найдите нужный факт в базе, затем настройте порог; не повышайте его автоматически для получения любого ответа.
- Ошибка доступа к глобальному кэшу uv: задайте доступный каталог, например `UV_CACHE_DIR=/tmp/itg-rag-uv-cache make check`.
